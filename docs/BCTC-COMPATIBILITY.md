# BCTC 配置兼容与连续切卡

## 用通用 JSON 表达匹配

兼容规则放在用户导入的 JSON 中。应用仍只有 EXACT、PREFIX、MASK 三种匹配方式，不根据卡名、来源或卡组织自动放宽匹配。

原 BCTC 本地服务收到 4 字节命令时比较前 4 字节，较长命令比较前 5 字节。例如录制的 GPO 为 `80A80000278325…`，终端金额、日期和随机数改变后，仍可通过 `80A8000027` 的 PREFIX 规则返回原回复。GENERATE AC 在原查找无结果或结果为 `6D00` 时，还会按前 2 字节 `80AE` 寻找回复。

转换采用内容匹配（`ordered=false`），按以下顺序保存：

1. 原完整 EXACT 命令及回复，既可精确回放，也可作为 DOL 诊断参考。
2. 对应的前 4/5 字节 PREFIX 规则，接受终端动态数据。
3. 每张含 GENERATE AC 的卡在末尾添加 `80AE` PREFIX，作为其他 GAC 输入的回退。

同回复且唯一的完整 EXACT 命令可供前缀匹配后的 PDOL/CDOL 诊断使用；有多份参考时不猜测。只有前缀时，诊断单独校验实际输入，并说明缺少完整参考数据。PREFIX 规则最短允许 2 字节，真实输入仍至少需要 4 字节命令头。

## 当前 34 张卡的转换边界

原卡共 169 对 APDU。转换后保留这些原规则，并增加兼容规则，共 349 条；所有回复、卡包 ID、卡片 ID 和 AID 均保持原值。11 张含 GENERATE AC 的卡各自只有一个 GAC 回复，而且不是 `6D00`，因此末尾回退没有歧义。

D00301 两条 SELECT 的前 5 字节相同，分别选择 `A000000152301001` 和 `A000000152301002`，回复不同。原应用遍历 HashMap 的优先级不稳定，无法定义可靠的同头回复顺序。转换保留完整 AID 作为这两条 PREFIX，允许 Le 改变或省略，同时明确区分两个应用；这是有意消除原实现的歧义。

当前源卡包没有仅 4 字节的命令。转换不会给每条长命令再添加 4 字节头规则：例如只有 `00A40400`、没有 Lc 和 AID 的 SELECT 无法区分 PPSE 与业务应用，原工具可能按遍历顺序返回任一回复。当前方案兼容完整命令的动态数据，不复现这类不完整输入的歧义。

如果未来配置包含同头非 SELECT 多回复、多个不同 GAC 回复，或 GAC 主规则返回 `6D00`，转换工具会拒绝，需人工拆分场景。不能用规则排列悄悄替原应用做批准或拒绝选择。

转换命令：`python tools/prepare-bctc-json.py <原始完整卡包.json> <兼容卡包.json>`。工具要求输入规则为 EXACT，避免重复转换；不向应用内置第三方卡包。更新现有包会整包替换，须使用包含全部卡片的文件，并先保留用户额外编辑的数据。

固定回复不会重算密文、动态签名或 ATC。兼容命令查找只保证能按配置返回数据，联机主机校验和脱机认证仍需有效测试条件及真实终端验证。

## 平台修复

鸿蒙 `HceService.stop()` 会同时取消 `hceCmd` 订阅。AID 列表变化时必须清除订阅标记和旧引擎，随后 start 并重新 on；失败时清理半成品。每次完成路由注册及订阅均记日志。复测重点是 D00401 → D00301 → D00401，多轮连续刷卡及退出后重新打开。

Android 没有相同的手动订阅流程。启动时增加 AID 注册回读与成功日志，HCE 服务增加创建、销毁、失活原因及禁用状态收包日志。用户反馈的“无新 APDU”尚未真机定位；回读成功只确认系统登记的路由配置，不代表射频硬件已收到命令。
